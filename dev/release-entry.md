## 83.2.1 ({{STAMP}}): the press plays your music, for real this time

- **WHY 83.2.0 WAS STILL SILENT.** The player was right; the file it was handed was not music. `scNativeCustody` passed its base64 chunks to Capacitor's `Filesystem.writeFile` without `encoding: 'base64'`, and the plugin's documented default is UTF-8 text - so a 1.2 MB song landed in the app's private files as **1,600,004 bytes of base64 letters**. `MediaPlayer` read the first bytes, found no audio header, and stopped with `native -> cannot decode this file`. The press routed perfectly, the service started, and the copy it played was noise.
- **HOW THAT WAS ESTABLISHED, NOT GUESSED.** The shipped page's own `scNativeCustody` was extracted and run under Node against a stub of the Filesystem plugin that behaves as documented, with a real 1.2 MB blob. On the 83.2.0 page: `writeFile np/current.mp3 encoding=(none)`, file 1,600,004 bytes, not identical to the song, and **no diag line at all** - which is why a device test could only ever say "still silent". The same harness on this page: 1,200,000 bytes, byte-identical, `copy -> 1200000 bytes ready`. A 3.1 MB song written across seven chunks is byte-identical too.
- **THE FIX.** Both writes now pass `encoding: 'base64'`, and the copy is not called ready until `stat` says it holds exactly the song's byte count. A copy that is text, short, or missing becomes a diag line and a fall-through, instead of a service that starts and dies quietly.
- **THE SAFETY NET, ALSO TESTED.** The same harness with a plugin that ignores `encoding` (an older Filesystem, or a future regression) ends with no `current.json`, `ready()` false, and the trail reading `copy -> the copy is 1600004 of 1200000 bytes`. The press then behaves as it did before 83.2.0, rather than starting a player that dies.
- **WHAT WAS CHECKED.** `dev/patch-8321.py --check` exits **1** before the payload and **0** after it, a second run is a no-op, and the page lands at 83.2.1 with the moved service-worker cache and a new changelog entry. The four harness cases (shipped page, 1.2 MB, 3.1 MB, encoding-ignoring plugin) are the evidence for the claim in the title. Rebuilt bundles: {{ROOT}} bytes on the full channel, {{PLAY}} on the store build.
- **NOT CLAIMED.** No phone has run this. What is proven is that the file the press plays is byte-for-byte the song, and that a bad copy can no longer be mistaken for a good one. Whether a particular OEM kills the foreground service on a swipe stays a device question, and the diag trail distinguishes the two: `native -> playing <title>` means the sound left the app, while `copy -> ...` means it never got there.

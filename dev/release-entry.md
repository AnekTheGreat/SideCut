## 83.0.6 ({{STAMP}}): the hidden player gets the app's own bridge

- **WHAT THE OWNER SAID.** *"still not working"*, after installing 83.0.5.
- **WHAT WAS ACTUALLY WRONG THIS TIME.** `GhostPlayerActivity` extended `BridgeActivity` directly - and Capacitor builds a page's plugin list when the activity creates its bridge, while this app registers its own `SideCutWidget` plugin in **`MainActivity`'s constructor** (`this.initialPlugins.add(SideCutWidgetPlugin.class)`, before `super.onCreate`, the ordering Capacitor 6 requires). A bare `BridgeActivity` subclass gets none of it. So the hidden player booted the page with no widget plugin at all: the page asked for `getPendingResume`, got "not implemented", caught it as `null`, and never pressed play. The trampoline was doing its job and starting a bridge that was deaf - which is why the press still ended in silence or in the app.
- **THE FIX, AND IT IS ONE WORD.** `GhostPlayerActivity extends MainActivity`. The hidden player is now the app itself - same bridge, same plugin list, same auto-registered npm plugins - just invisible: alpha 0, its own task, no recents entry. It inherits the constructor registration, so the page inside it can see the pending resume and press play.
- **A PRESS THAT DOES NOTHING NOW SAYS WHY.** `GhostDiag.java` writes five short breadcrumbs into the widget's own preferences, newest first: the switch, the press, which branch the trampoline took, the player booting, whether audio arrived, and why it stopped. `getGhostDiag` hands the trail to Settings → Widget, which shows it under the switch, refreshed when the tab opens. Two releases were spent guessing; this ends that.
- **THE FALLBACK IS QUICK NOW.** The hidden player looks 5 s after boot and every 3 s after that, and if it never makes a sound in about 12 s it opens the app - instead of the 20 s of nothing 83.0.5 had. A song that played and then ended still closes silently.
- **WHAT WAS CHECKED.** `python3 dev/patch-8306.py --check` exited **1** before the payload and **0** after it, and a second run was a no-op; the page boots in jsdom, the Widget tab opens, the trail row is there and stays hidden when there is no native side, and a tap on the switch stores `sidecut_ghost_play=1`. The native chain was run end to end on a sandbox Android project - `patch-widget.py`, then `dev/widget-sizes.py`, then `dev/ghost-host.py` - producing `GhostPlayerActivity extends MainActivity`, breadcrumb calls in all three places, a well-formed manifest declaring both activities, balanced braces and parentheses in all five Java files, and an identical tree on a second run. The rebuilt bundles reached their fixed point in the release commit: {{ROOT}} bytes on the full channel and {{PLAY}} on the store build.
- **NOT CLAIMED.** No phone ran this. What is proven from the code: the hidden player now builds the same bridge as the visible app, so the plugin the resume depends on is present - which it demonstrably was not in 83.0.5. What is still a device question: whether an alpha-0 window keeps WebView audio alive, and what the page's own restore does with a song whose process was killed. If it still fails, the trail in Settings → Widget will name the step that stopped, and the press falls back to opening the app within seconds.

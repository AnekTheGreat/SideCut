## 83.0.9 ({{STAMP}}): the widget press actually plays

- **WHAT THE OWNER SAID.** *"now it doesn't play anything"*, after installing 83.0.8.
- **WHAT WAS ACTUALLY WRONG, AND IT WAS MINE FOR THE THIRD TIME.** Every build since 83.0.5 blamed the wrong half. The page's resume called `play()` without ever putting the song on the audio element: `restorePlaybackState()` deliberately gives up on a song that has no object URL yet, so on a fresh process the element sat there with no `src`, `play()` rejected with `NotSupportedError`, and the press could only ever be silence. Worse, the page reported that miss through `ghostStep(...)`, and the plugin cleared the pending request on *any* report - so the first attempt, 700 ms into boot while the library was still hydrating, deleted the press. The three later attempts then read "nothing pending" and did nothing. One press, one early miss, no music, every time.
- **THE FIX.** (1) The resume puts the song on the element itself - it rebuilds the blob URL from the file that is still in the library, and retries once with a fresh URL when a reclaimed one is refused. (2) A miss is no longer a verdict: the page asks again every 600 ms for about forty seconds, until audio is really playing. (3) Only `playing ...` settles the request natively, and a request older than two minutes is dropped instead of resuming days later. (4) The hidden player now waits ~40 s for the song before opening the app, so it cannot give up at the moment the music was about to start.
- **WHAT WAS CHECKED.** `python3 dev/patch-8309.py --check` exits **1** before the payload and **0** after it, a second run is a no-op, the page lands at 83.0.9 with a new cache name and changelog entry, and every inline script still parses under `node --check`. The native chain ran end to end on a sandbox Android project - `patch-widget.py`, `dev/widget-sizes.py`, `dev/ghost-host.py` - with balanced braces, a well-formed manifest declaring both activities, and an identical tree on a second run. The rebuilt bundles reached their fixed point in the release commit: {{ROOT}} bytes on the full channel and {{PLAY}} on the store build.
- **NOT CLAIMED.** No phone ran this. What is proven from the code: the resume can no longer call `play()` on an element with no source, and no miss can delete the request before the library is ready. What is still a device question: whether an alpha-0 window keeps WebView audio alive at all. If it does not, the trail in Settings → Widget will say `player -> no audio, opening the app`, and pressing the widget will at least open the app with the song already resumed.

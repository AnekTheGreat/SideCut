## 83.2.2 ({{STAMP}}): a bad copy can no longer swallow the press

- **WHY 83.2.1 STILL LOOKED BROKEN.** 83.2.1 fixed the writer; it did not touch the copy already on the phone. The 1.6 MB of base64 text that 83.2.0 saved was still at `files/np/current.mp3`, and `NativePlayService.audioFile()` only asked two questions - does it exist, is it longer than zero bytes - and garbage answers yes to both. So the press still routed to the native player, the player still started, `MediaPlayer` still refused the file, and the press still ended in silence. Nothing about 83.2.1 could be seen on a phone that had already been through 83.2.0.
- **THE FIX.** The first bytes decide now, not the file name. A copy whose header is not a container is deleted along with its json, so the same press falls through to the older hidden player instead of starting a player that dies, and the trail records `native -> the copy on disk is not audio, throwing it away`.
- **HOW IT WAS TESTED.** The new header check was extracted from the shipped `dev/native-play-service.java.txt`, compiled with a JDK and run against 13 real files: the exact 1.6 MB base64 copy 83.2.0 produced, a short base64 fragment, a tagless text file, an empty file, a three-byte file and a zero-padded file (all rejected), plus ID3-tagged mp3, bare-frame mp3, flac, ogg, wav, m4a and amr (all accepted). 13 of 13 verdicts correct. The page half was extracted from the built page and run in Node: with the switch on and nothing recorded the breadcrumb box now appears and says so; with the switch off it stays hidden; a real trail is shown verbatim. The copy writer was re-run against a documented Filesystem stub and is still byte-identical to the song.
- **CHECKS ON THE BUILD.** `dev/patch-8322.py --check` exits 1 before the payload and 0 after it, a second run is a no-op, all seven edits are applied in one pass, and nothing is written unless every edit fits. The page parses clean, the service-worker cache moves to 83.2.2, and the changelog entry is in place. Rebuilt bundles: {{ROOT}} bytes on the full channel, {{PLAY}} on the store build.
- **NOT CLAIMED.** No phone has run this. What is proven is that a non-audio copy can no longer be mistaken for a song, so a press either plays it or says why it will not. If a press is still silent with 83.2.2, the trail on Settings -> Widget now names the step, and the three lines to look for are `copy -> <n> bytes ready` (the page wrote a real song), `native -> the copy on disk is not audio, throwing it away` (an old broken copy was found and dropped) and `native -> playing <title>` (the sound left the app).

## 83.0.5 ({{STAMP}}): the widget plays without opening the app, for real

- **WHAT THE OWNER SAID.** Two words, after installing 83.0.4: *"it doesn't work"*.
- **WHAT WAS ACTUALLY WRONG, AND IT WAS OURS.** 83.0.4 chose the play button's intent when the widget was PAINTED: `ghostPlayPossible()` answered "no" whenever SideCut was alive, and SideCut is the only thing that ever paints this widget (`updatePeriodMillis="0"`, so the launcher never asks for a redraw by itself). The intent baked into the button was therefore the one from the last paint - which always happened while the app was running. The hidden-host branch was almost never reachable: the press took the old path, sent a media key to a dead process, and opened the app. The feature was not unreliable; it was, in practice, never installed.
- **THE FIX IS WHERE THE DECISION LIVES.** Nothing is decided at paint time any more. With the switch on, the play button always opens `GhostHostActivity` - a transparent trampoline with no bridge and no content - and the trampoline reads the phone at the moment of the press: music already playing, or a heartbeat fresher than 90 seconds (the app is still behind the widget), and it re-sends the widget's own `WIDGET_playpause` broadcast and finishes, so every press behaves exactly as it did before this release. Only when the app is really gone does it start `GhostPlayerActivity`, the alpha-0 `BridgeActivity` that boots the page off-screen and resumes the last song.
- **THREE MORE THINGS 83.0.4 GOT WRONG.** The off-screen WebView now allows playback without a tap (`setMediaPlaybackRequiresUserGesture(false)`) - the page presses play on its own boot, and Chromium refuses that otherwise. The hidden player waits 8 s before its first look and 20 s of silence before giving up, instead of closing itself after 10 s. And when it gives up it OPENS THE APP, so a press can end in the app but never in nothing; a song that played and then ended still closes silently.
- **THE SWITCH STOPS LYING.** The switch lives in the page, which updates over the air, so it appeared on installs whose Android build carries no hidden player at all - storing a choice nothing reads, which looks exactly like a broken feature. Settings → Widget now writes the choice, reads it back out of the widget's own preferences through `getGhostPlay`, and if the phone does not confirm it, says so: *"Saved, but this Android build has no hidden player - install the new SideCut build"*.
- **WHAT WAS CHECKED.** `python3 dev/patch-8305.py --check` exited **1** before the payload and **0** after it, and a second run was a no-op; the page boots in jsdom, the Widget tab opens, the switch is in it and a tap stores `sidecut_ghost_play=1`. The native chain was run end to end on a sandbox Android project - `patch-widget.py`, then `dev/widget-sizes.py`, then `dev/ghost-host.py` - producing a well-formed manifest declaring both the trampoline and the hidden player, a provider whose play button reads `ghostPlayOn(ctx) ? ghostPi(ctx) : pi(ctx, "playpause", "")` (a paint-time question that can no longer be stale, because it no longer asks about the app's state), balanced braces and parentheses in all four Java files, and an identical tree on a second run. The rebuilt bundles reached their fixed point in the release commit: {{ROOT}} bytes on the full channel and {{PLAY}} on the store build.
- **NOT CLAIMED.** No phone ran any of this, and nothing was listened to. The build is where a device question still lives: whether a given Android release lets an alpha-0 activity keep WebView audio alive, and whether the page's boot resume actually finds a song after the process was killed. What this release fixes is something that can be proven from the code alone - the press now reaches the hidden player at all - and it makes the failure mode honest: if the phone cannot do it, the switch says so and the press opens the app.

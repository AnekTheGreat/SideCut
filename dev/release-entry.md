## 83.2.0 ({{STAMP}}): the music stops living in the window

- **WHY THE LAST THREE BUILDS COULD NOT WORK.** Every version up to 83.1.0 played music with an `<audio>` element inside the app window. Swiping SideCut out of recents destroys that window, and the sound dies with it. The "hidden player" from 83.0.4 was itself a WebView, so it inherited the same death, and no patch to the press could bring back a player that was gone. That is the difference from Spotify: a native player is not in the window at all.
- **WHAT THIS DOES.** The dead-app press starts `NativePlayService`: `android.media.MediaPlayer` inside a foreground service, which a recents swipe does not remove. It plays a copy of the current song that the page leaves in the app's private files (`np/current.<ext>` plus `np/current.json` naming it, with title and position), so the press needs no activity, no WebView and no page to answer. Pressing again pauses it; opening the app hands playback back to the page, so the same song never plays twice.
- **WHAT IT DOES NOT DO YET.** The native player handles the one song it holds a copy of. It does not skip through the queue, and it does not drive the widget's title or progress while it runs, because the page does that when it is open. It is the "press play with nothing open and music comes out" path, which is exactly the one that was silent.
- **THE COPY COSTS SPACE.** One song's worth, in the app's own storage, rewritten only when the song changes. A library that has never played anything has no copy, the service reports it is not ready, and the press behaves as it did before.
- **WHAT WAS CHECKED.** The native chain ran end to end on a sandbox Android project - `patch-widget.py`, `dev/widget-sizes.py`, `dev/ghost-host.py`, `dev/ghost-route.py`, `dev/native-play.py` - and a second run of `dev/native-play.py` is a no-op. The manifest parses with the service **inside** `<application>` (`mediaPlayback`, `stopWithTask=false`, both foreground-service permissions, VIBRATE still present) and all seven Java files are brace- and paren-balanced. `python3 dev/patch-8320.py --check` exits **1** before the payload and **0** after it, a second run is a no-op, all seven inline scripts still parse, and the page lands at 83.2.0 with a new cache name and changelog entry. The rebuilt bundles reached their fixed point in the release commit: {{ROOT}} bytes on the full channel and {{PLAY}} on the store build.
- **NOT CLAIMED.** No phone ran this, and this environment has no Java compiler, so the first real compile of `NativePlayService.java` is the CI build. What the code says: the press starts a foreground service instead of a window; the service plays a local file with `MediaPlayer`; and if the file is missing, unreadable or undecodable the diag lines say so (`native -> nothing on disk to play`, `native -> cannot decode this file`) instead of failing silently. What remains a device question is whether an OEM kills the service anyway, and how long the first copy of a large song takes to write.

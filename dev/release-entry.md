## 83.0.7 ({{STAMP}}): the press stops lying about what it did

- **WHAT THE OWNER SAID.** *"there's no crash thing it just doesn't plainly work"*, after installing 83.0.6. No error, no dialog, no sound.
- **THE BUG THIS RELEASE IS BUILT AROUND.** The trampoline decides whether to hand a press back to the widget by asking whether SideCut is "still alive", and it answers that from a heartbeat the page writes while it runs - a heartbeat that stays fresh for **90 seconds after the process is dead**. So the sequence anyone testing this actually performs - play something, swipe the app away, press the widget - happened inside that window: the press was handed to a player that no longer existed. Nothing played, nothing crashed, nothing said why. That is exactly the shape of the report. A hand-back is now only the first half of a decision: it gets 2.5 s to produce sound, and if the phone is still quiet the hidden player starts anyway.
- **A PRESS THAT ARRIVES EARLY IS NO LONGER THROWN AWAY.** Reading the pending resume *consumed* it, so a request read a moment before the library finished hydrating found an empty queue, and the press was gone for good. Asking no longer consumes (`ghostAskResume`); the request is cleared by the page's answer instead (`ghostStep`), and the page now asks at 700 ms, 2.5 s, 5 s and 8 s instead of once.
- **THE PAGE SAYS WHERE IT STOPPED.** Four silent failure points - nothing queued, the queued song has no file loaded, pressing play, playing - now each report through the plugin. A resume that finds nothing used to look identical to a press that never arrived.
- **AND IT SAYS SO ON THE PHONE.** Every breadcrumb now also posts as a low-importance notification, so a press that does nothing can be read on the shade without opening the app and digging into Settings. The trail in Settings → Widget stays, newest first, twelve lines.
- **THE HIDDEN PLAYER TRUSTS THE PAGE OVER THE PHONE.** `isMusicActive()` is a guess about the whole device and it can be wrong while the first buffer fills. When the page reports that its `play()` resolved, the player counts that as sound and stops treating it as a failure.
- **WHAT WAS CHECKED.** `python3 dev/patch-8307.py --check` exits **1** before the payload and **0** after it, a second run is a no-op, the page lands at 83.0.7 with a new cache name and changelog entry, and all seven inline scripts still parse under `node --check`. The native chain was run end to end on a sandbox Android project - `patch-widget.py`, `dev/widget-sizes.py`, `dev/ghost-host.py` - producing `GhostPlayerActivity extends MainActivity`, `handBackThenPlayer`, `pageSaysPlaying`, `ghostStep`, `ghostAskResume`, a well-formed manifest declaring both activities, balanced braces and parentheses in every Java file, and an identical tree on a second run. The rebuilt bundles reached their fixed point in the release commit: {{ROOT}} bytes on the full channel and {{PLAY}} on the store build.
- **NOT CLAIMED.** No phone ran this. What is proven from the code: the hand-back can no longer end in silence without starting the hidden player, and a press read too early is no longer lost. What is still a device question: whether an alpha-0 window keeps WebView audio alive, and what the page's own restore does with a song whose process was killed. If it still fails, the shade will name the step that stopped - the press, the branch, the player boot, or the page's own account of the resume.

## 83.0.4 ({{STAMP}}): the widget plays without opening the app

- **WHAT THE OWNER SAID.** *"the widgit should be able to play the music like Spotify even when the app is swiped away from recents and fix other audio issues"* - and, when told what it would take: *"do it but test only on FULL version not release version"*.
- **WHY IT COULD NOT WORK BEFORE.** SideCut's sound comes out of the WebView. Swiping the task away destroys the activity, the WebView with it, and with it the `<audio>` element that was playing. What is left is a widget with nothing to press: it leaves a resume request and opens the app, because there is no player in the process to hand the press to. Spotify does not have this problem because its player is a native service that survives the task; SideCut's player is a page.
- **THE ANSWER, AND WHAT IT IS CALLED.** A hidden host. `GhostHostActivity` is a translucent `BridgeActivity` in a task of its own, never in recents, with its whole view tree at alpha 0: it boots the same page off-screen, writes the resume request *before* the bridge is built (so the page's own boot finds it and presses play on the song the restore put on the deck), and shows nothing at all. It watches `AudioManager.isMusicActive()` every five seconds and closes itself after two silent polls - so a host with nothing to play, or one whose song has ended, leaves no trace. The play button on the widget becomes `PendingIntent.getActivity` **only** when the app is genuinely gone (no fresh heartbeat, no music) and the switch is on; every other case keeps the media-key press it has always used. That is also what makes the launch legal: a widget's own activity PendingIntent is user interaction, whereas a receiver calling `startActivity` in the background is refused on Android 10+.
- **OFF UNTIL ASKED FOR.** Settings → Widget gains one switch, "Play without opening the app", default off. It writes `sidecut_ghost_play` on the page and `ghostPlay` in the widget's preferences through a new `setGhostPlay` plugin method, which repaints the widget immediately so the button switches over without waiting for a heartbeat. With it off, 83.0.3's behaviour is untouched.
- **HOW THE NATIVE HALF SHIPS.** `dev/ghost-host.py`, run by `android-build.yml` right after `dev/widget-sizes.py` - a `dev/` script because `.github/workflows/` cannot be committed by an Actions token, which is the same rule that put the widget's extra placements in `dev/`. It writes `GhostHostActivity.java`, adds one `<activity>` to the manifest, puts `ghostPlayPossible`/`ghostPi` in the provider, and the two switch methods in the plugin. Idempotent, and marked `83.0.4: the widget plays without opening the app`.
- **WHAT WAS CHECKED.** `python3 dev/patch-8304.py --check` exited **1** before the payload and **0** after it, and a second run was a no-op; every inline script compiles; the patched page boots in jsdom, the Widget tab opens and the new switch is in it, and tapping it stores `sidecut_ghost_play=1`. The native chain was run end to end on a sandbox Android project - `patch-widget.py`, then `dev/widget-sizes.py`, then `dev/ghost-host.py` - and produced a well-formed manifest carrying the translucent activity, a provider whose play intent reads `ghostPlayPossible(ctx, playing) ? ghostPi(ctx) : pi(ctx, "playpause", "")`, a plugin carrying both switch methods, balanced braces and parentheses in all three Java files, and an identical tree on a second run. The full-flavour APK is what the build produced and what was inspected; the Play build was left alone, as asked.
- **NOT CLAIMED.** No phone ran any of this, and nothing was listened to. Whether a particular Android build lets the off-screen host keep its audio, how a launcher treats a translucent activity in its own task, and how the hand-off feels when the app is opened mid-song are all device questions. What is proven is the code the widget press reaches, the manifest entry it is declared by, and the switch that decides it - not the sound.
